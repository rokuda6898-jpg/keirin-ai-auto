# 管理体制

5担当は独立した自動検査の責任区分であり、人間や常駐AI社員を新規採用したという意味ではない。
既存 site-manager がデータ取得・結果集計を修復し、management-audit は読み取り専用で検査する。
監査は予想の書換え・モデル昇格・締切後補充を行わない。

## 現在の通知設定

利用者の受信済みメールでGitHub Actionsの「Run failed」通知を確認したため、現在は同じ経路を使用する。SMTP・アプリパスワードは不要。異常が新規または24時間継続した場合、監査結果保存後にジョブを失敗終了させる。メール配信はGitHubアカウントのActions通知設定に従い、ジョブ失敗だけをもってメール到着とは断定しない。復旧時のメールは保証せず管理画面で確認する。既存SMTP用Secretsは参照しない。

## 別方式として残すSMTP通知設定（現在は使用しない）

GitHub Settings → Secrets and variables → Actions に以下を登録する。
送信先や認証情報は公開ファイル・Issue・チャットに記載しない。

- SMTP_HOST: 利用するメール送信サービスのホスト
- SMTP_PORT: 通常587（STARTTLS）、465（接続時TLS）。未設定は587
- SMTP_USER / SMTP_PASSWORD: 送信サービス専用の認証情報
- ALERT_FROM: サービスで送信を許可された差出人
- ALERT_TO: 利用者が承認した通知先

設定後 nexus-management-audit を手動実行し、管理画面の email_status と実際の受信を確認する。
SMTP受理は受信箱への到着を保証しない。設定未完了は未設定として表示する。
異常クラスが同じなら24時間メールを抑制。復旧は1回通知。
抑制状態はActions cacheに保存されるため、キャッシュ削除時は再通知される。
GitHub全体が停止すればこの監視も通知できない。独立サービスでの外形監視は別途必要。

## 精度監査の限界と次の検証

- 会社の現在の集約は部署ごと等重みの順位投票。部署間の相関は補正していない。
  重複率は診断値であり、重複しているだけで部署を除外しない。
- 過去の38.77%は探索を重ねた期間の結果。未使用期間または将来の固定予想で再検証が必要。
- 同じ初回事前予想でも生成時刻は方式ごとに異なる。厳密な同時点実験では同じ入力スナップショットが必要。
- 管理画面の共通レース比較は各点100円。候補不足を埋めないため点数と総額が同一とは限らず、優劣確定には使わない。
- 現在の管理画面は会社・独立予想の最大1件払戻依存度。リスク部単独の高配当依存度は別の同条件台帳検証が必要。
- 不明払戻はゼロにしない。同着の各的中買い目を別々に照合。
- 予想未作成を後付けして全レース達成に見せない。作成率と的中率を別々に報告する。

異常時は責任担当・レースID・確認時刻を保存し、修復後の検査で解消を確認する。
休催・中止・延期の判定は現時点で自動確定できないため、未取得と区別して担当が確認する。
