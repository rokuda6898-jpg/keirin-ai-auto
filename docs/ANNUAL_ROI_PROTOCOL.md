# 年間Nexus・100円均等買いの回収率検証

## 目的と現在の状態

対象は `models/nexus53/manifest.json` に保存された、2025年10月9日〜2026年10月8日の元Nexusです。条件付き3連単の別モデル・数日間の8点研究・5,000〜10,000円配分へ対象を置き換えません。

| 固定する元基準 | 値 |
| --- | ---: |
| レース数 | 27,351 |
| 的中レース数 | 14,729 |
| 的中率 | 53.8517787% |
| 購入額 | 43,596,000円 |
| 払戻額 | 33,783,680円 |
| 回収率 | 77.4926140% |
| 購入額÷100円の換算点数（元明細は未照合） | 435,960点 |

2026年10月20日時点で、この元年の全レース買い目・完全確率・公式払戻を結合した原明細は入手できていません。**現時点ではこのCLIによる年次再現・候補の年次評価は未実行です。** `schema` は入力仕様を出すだけで、仮の年間成績を生成しません。単体テストの4レースは人工データです。

別出力にある13,612・13,742レースや、集計値だけのmanifestから27,351レースの個別予想を復元して扱うことはできません。現在の `flexible-first-v1` は元の年次方式に後から加わった買い目変更です。本研究の `original_tickets` はその変更前の6/15/24点です。以前の「14,728的中／77.497%」と「100倍以上265件」は、元の計算明細・定義をまだ照合できていません。

## なぜ的中率53.85%でも回収率77.49%なのか

元エンジンは、予測したレース分類で6/15/24点を決め、買い目の確率合計を大きくするフォーメーションを選びます。払戻期待額を直接最大化する目的関数ではありません。元実績の平均購入点数は15.93945点、1レース当たり購入額は1,593.95円、払戻額は1,235.19円です。年間の差額はマイナス9,812,320円になります。

同じ購入額で回収率100%へ到達するには、払戻額を約29.04%増やす必要があります。払戻額が全く落ちないと仮定して点数だけを減らすなら、購入額の約22.51%削減が必要です。これらは目標までの差を示す算術であり、点数削減で払戻が維持できるという予測ではありません。

## 先に固定する候補と時間分割

候補は同じ完全確率 `q` を使った、固定6点・8点・10点・12点の4案だけです。学習モデル、校正値、元の入力は変更しません。条件付きモデルの別年・別集団で得られた8点規則を流用しません。

各候補は `nexus_model.optimizer.select` の既存探索を使います。確率上位の集合が4フォーメーション以内に完全収納できればその集合を採用し、できなければ既存の宣言済み探索範囲で確率合計を評価します。したがって常に「制約なしの上位k点」と一致する保証や、あらゆるフォーメーションに対する大域的な最適性の主張はありません。全レースについて、選んだ点数とフォーメーション展開が完全一致し、重複がないことを検査します。

| 区間 | 日付 | 用途 |
| --- | --- | --- |
| 開発 | 2025-10-09〜2026-04-08 | 4案を比較し、回収率最大の1案を選ぶ |
| 時間順の検証 | 2026-04-09〜2026-10-08 | 選択済みの1案だけを評価する |

開発の回収率が同じ場合は、点数が少ない案、的中率が高い案、候補IDの順で決めます。回収率比較には整数額の比を使います。会場・勝った日・結果配当によるレース除外や、後半を見た後の閾値変更は行いません。累積確率閾値や点数の追加系統を同時に探索することも、このプロトコルには含めません。

この年はすでに繰り返し研究されています。後半を**未見のholdout**とは呼びません。

## 入力の最低限の形

入力はUTF-8のJSONL、または`.jsonl.gz`です。全27,351レースについて1レース1行を必要とします。元年のレースID一覧を別cohortファイルとして用意し、件数だけでなくID集合を一致させます。原データが欠けていても、揃ったレースだけで代用しません。

```json
{
  "schema": 1,
  "race_id": "011220251009",
  "date": "2025-10-09",
  "cars": [1, 2, 3, 4, 5, 6, 7],
  "q": null,
  "original_tickets": [],
  "original_formations": [],
  "model_id": "nexus-formation-5385-v1",
  "model_manifest_sha256": "供給した元モデルmanifestファイルのSHA-256",
  "training_cutoff_exclusive": "2025-10-09",
  "outcome": {
    "status": "settled",
    "payouts_per_100_yen": {},
    "refund_tickets": [],
    "refund_all": false
  }
}
```

上は**項目だけを示す不完全な見本**です。空の買い目・払戻を実データとして受け付けるものではありません。

- `cars` は元モデルの車順を保存します。後から車番順へ並べ替えてはいけません。
- `q` は `itertools.permutations(cars, 3)` の順で全3連単の確率を格納します。7車なら210、9車なら504個です。上位の数点だけを合計1へ正規化した配列は代用になりません。元基準の精算監査だけなら`null`を認めますが、候補実行前には全レースの完全qを要求します。
- `original_tickets` は重複のない元の6/15/24点です。`original_formations` は `{ "first": [1], "second": [2,3], "third": [4,5], "count": 4 }` のような完全展開するブロックを1〜4個持ちます。
- `outcome.payouts_per_100_yen` は、公式に的中した全組み合わせの**100円当たり確定払戻額**です。同着は複数の的中組を残します。オッズ倍率や推定値を金額として渡してはいけません。
- 返還は `refund_tickets` に明示します。レース全体の返還なら `status: "refunded"`、`refund_all: true`、的中払戻は空です。返還を的中件数へ加えません。
- `snapshot_at` と `close_at` を渡す場合は、実際にレース当日に締切前へ保存した予想時刻を意味し、両方必要です。`input_captured_at` がある場合は `input_captured_at <= snapshot_at < close_at` を要求します。後日取得した原資料の時刻は別のprovenance項目へ残してください。`feature_history_through` がある場合は当該レースの前日以前を要求します。欠けた過去時点の証拠を補って、事前保存だったとは扱いません。
- `source_url`、`source_sha256`、`input_sha256` は原資料と対応させる監査情報です。予想生成時の `prediction.replay_evidence` からこれらを保存できても、既存の過去予想へ後から補填しません。

現在の変更範囲は、この入力契約と検証補助の準備です。将来予想の完全qを日別台帳へ自動保存する処理は、まだ開始していません。既存のEngineやpublisherが完全qの保存を始めたという意味ではありません。

cohortファイルの必須項目は以下です。

```json
{
  "schema": 1,
  "benchmark_id": "nexus-27351-2025-10-09-2026-10-08",
  "model_manifest_sha256": "元モデルmanifestファイルのSHA-256",
  "source_description": "元研究の全レース一覧を取り出した原資料の説明",
  "source_sha256": "その原資料のSHA-256",
  "race_ids": ["元の27,351個のレースIDを重複なく記載"]
}
```

購入額は常に`100円 × 全レースの全選択点数`です。的中組の公式払戻額と返還額を合計して回収率を求めます。公式確定払戻は**精算だけ**に用います。したがって100円均等買いの再計算に締切前オッズの保存は必須ではありません。締切後の配当を候補選択へ渡すことは禁止し、選択関数の引数も`cars, q, points`だけに限定します。

返還のあるレースも元cohortに残し、購入額の分母は減らさず、返還券1点につき100円を払戻の分子へ足すgross方式です。これは返還額を購入額から引くnet方式のライブ集計と異なります。元年がどの返還慣行を使ったかは原資料照合まで未証明であり、基準が一致しなければ原因を原資料へ戻って確認します。返還レースの除外や払戻額の調整で一致させません。

## 再現ゲートとコマンド

```bash
python src/nexus_roi_research.py schema --output /path/to/input_contract.json

python src/nexus_roi_research.py audit \
  --ledger /path/to/original_annual.jsonl.gz \
  --cohort /path/to/original_cohort.json \
  --model-manifest /path/to/original_model_manifest.json

python src/nexus_roi_research.py prepare \
  --ledger /path/to/original_annual.jsonl.gz \
  --cohort /path/to/original_cohort.json \
  --model-manifest /path/to/original_model_manifest.json \
  --output-dir /path/to/new_empty_study_directory

python src/nexus_roi_research.py develop --run-dir /path/to/new_empty_study_directory
python src/nexus_roi_research.py validate --run-dir /path/to/new_empty_study_directory
```

`audit` は元レースの集合、日付、元モデル、6/15/24点、フォーメーション完全展開、公式結果を検査し、元の27,351／14,729／43,596,000円／33,783,680円を整数で照合します。どれかが違う場合、終了コード2と`status: blocked`を返し、候補成績を出しません。欠けた入力を埋めたり、欠測レースを見送ったことにしたりしません。

19個のモデル資産hash、学習終端、校正、買い目方式、元の集計情報から計算する固定指紋は `d7ad899a9280e673608f1fed533423b22b79e04b8ab63be1ff2766b6c22e1ed5` です。これらと各レースが宣言するモデルmanifest hashを照合します。学習締切は年の最初で固定し、年の後半まで学習した確率を元モデルとして受け付けません。ただし、宣言hashの一致は全件再推論の証明でも、歴史的な入力取得時点の証明でもありません。

`prepare` は、完全qが全件存在してから入力ファイル・コード・候補・時間分割のhashを固定します。`develop` は開発側だけの4候補明細と選択を保存します。`validate` はその選択済みの1候補だけを後半へ適用します。中断時はprotocol・入力・コード・選択hashがすべて同じ場合に限り、同じ計算を再開できます。保存済みの予測明細があれば一致を検証してそのまま使い、完了済みの結果も変更せず再利用します。別候補や変更後の条件での再評価は認めません。同じ計算の復旧は、後半を見て条件を変える追加試行とは区別します。

## 評価結果の扱い

検証レポートには、全期間と後半の的中率・回収率・購入額・払戻額を元方式と並べます。点数削減に伴う的中率低下も表示します。さらに、新方式の最大払戻が発生した1レースを**両方式から同じように**除いた感度を示します。この結果を見て選択条件を再調整しません。

この研究の到達判定は、開発と後半で元方式より回収率が改善し、全期間・後半・最大払戻1件除外の各回収率が100%を超えることです。条件を満たしても将来の利益を証明したとは扱いません。サイトのモデルはこのCLIから変更しません。

「100倍以上」の診断を出す場合は、100円当たり10,000円以上の公式的中券を少なくとも1点買ったレース数と定義します。同着でも1レースは1件、返還は除外です。以前の265件と同一定義であるとは、原明細照合まで主張しません。
